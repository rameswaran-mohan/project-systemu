# v0.10.31 - a gate that resumes, a page that never blocks, a stop that stops

### Fixed
- **`daemon stop` never terminates a process that is not a systemu daemon.**
  The PID in the pid file is checked against its command line and start
  time before anything is signalled; a stale file names the PID it refused
  and how to clear it.
- **A refused `daemon start` creates nothing.** The dashboard-extra check
  runs before the vault is opened, so a refusal on a bare install leaves no
  vault tree behind.
- A failed readiness verdict is ASCII and prints the vault and log paths on
  one line each; `daemon status` keeps paths only on unwrapped lines outside
  the panel, and `census grant --help` names every exit code it can return.
- **The Chromium probe reads the filesystem and never starts the driver.** On
  the browser install a healthy daemon start no longer prints asyncio errors
  and a Playwright traceback; presence is decided from Playwright's own
  browser registry and the executable on disk, a present Chromium is
  witnessed in the log, and an unreadable registry reads as unknown with its
  reason on one line.
- **A refused consent file is named.** When a census consent file exists but
  is refused (a stale generation after a revoke, a signature mismatch, or a
  missing generation anchor), `census status` says so and why instead of
  reading like "never granted".
- **One daemon per vault and port, and the daemon names its interpreter.** A
  second `daemon start` in the seconds between the parent writing the pid
  file and the child overwriting it, or after any stop, could spawn a real
  rival on the same socket; the single-instance guard is now keyed on the
  daemon's own published identity plus PID liveness. The ready line prints
  the interpreter path the daemon runs under, `daemon status` compares it
  with the one you invoked and says so loudly when they differ, and a test
  walks every process-spawning call to confirm none names Python by a bare
  name. What looked like a double-spawn under a Windows venv is the venv
  launcher stub and its child: two processes with the same arguments, one
  daemon, and the banner now knows the difference.
- **Approving a tool-run gate resumes the run.** Since gates became resumable,
  a guard from the chat-only era at the top of the resume rail refused every
  run that was not dispatched from chat (forge heal sweeps, scheduled runs,
  recovery re-dispatches): the card resolved and nothing followed. Approve
  once now resumes through the single-use approval bridge and writes
  "Resumed after your approval"; Always allow resumes and remembers; Deny
  ends the run in a readable state; a refused bridge is an event you can
  read, never silence; and the card says what each button actually does.
- **No network probe runs while a dashboard page renders.** Provider status
  comes from a snapshot kept fresh by a background refresher; the layout,
  the health banner, Settings, and the trust card read it and never open a
  socket, the first render says "checking providers" until the first
  snapshot lands, and a stale snapshot says how old it is. This is the
  blocking connect that froze the renderer and ate clicks.
- **The multi-daemon banner counts live daemons, not history.** Every entry
  is verified alive (a reused PID or a process no longer running the daemon
  does not count), duplicates collapse, stale records are pruned, and the
  banner names each live PID with its port and interpreter. The danger
  wording appears only when two verified daemons share a port.
- **A chat submission is never lost.** The composer clears only once the
  submission is acknowledged; if the run cannot start, the text stays and a
  toast names the reason.
- **Stop really stops.** The Stop button cancels the running chat task through
  the runtime, including one parked on an approval card (the card is withdrawn
  with a note), and says what it stopped or exactly why it could not. A task
  restored after a daemon restart with no live worker is shown as such, with
  the way out.

### Changed
- Every outbound User-Agent carries the package's own version, from one
  helper; the reclassify option label and the bulk first-gate card are ASCII
  (the card's golden was re-frozen deliberately for that one change).
- Approval cards are ASCII (tool-run and blocked-tool cards).
- One chat task runs at a time. A submission while one is running is refused
  with a toast naming the running task and what to do; `/continue` on a task
  waiting on an approval says what it is waiting on and where to resolve it.
